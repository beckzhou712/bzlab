Redesigning for the Second Round

25 Aug, 2026
|Edit page

The first round of this benchmark was small — a pilot, strictly speaking, meant to prove the pipeline runs end to end and to give a rough sense of where the interesting differences might show up. For this second round I substantially expanded the corpus, and improved the experimental design based on the pitfalls the first round walked into.

1. Trimming facets and query types

The last round used a fairly large number of facets and query types. The query types mainly came from the three types proposed in Prompting datasets: Data discovery with conversational agents — a paper cited by Keywords are not always the key — plus keyword. After discussing it with Juliana, we concluded that the table as it stands is too big and that some of the facets don’t discriminate well, so we should trim down to a subset. Two facets are worth discussing separately.

The first is the schema facet, which in the original design was basically about querying exact column names. This one was cut, for two reasons. First, it’s a meta-facet: naming a date column collides with the temporal feature, and naming a geographic column collides with the spatial feature, so it inherently overlaps the other facets and shouldn’t stand as an independent category. Second, it carries its own confounding (see my previous post).

Vocabulary mismatch was also dropped as a standalone dimension (which I discussed in an earlier post as well). It’s a meta-facet too, and I decided to evaluate how well the different retrieval representations handle it in a different way. After the LLM produces a base query, I generate wording variations of that query; the n variations and the base query all trace back to the same dataset, which serves as the known-item ground truth for computing hit@k, and each arm’s vocabulary-mismatch ability then gets judged under different values of top-k. There are some further design pieces that keep a wording variation an actual rewrite rather than something that drifts off, but I won’t go into those here.

At the same time, I adjusted the definitions of the facets and query types that were kept, trying to hold them orthogonal and clear. I also designed some steps to address the problem of how to get the model to generate queries that match the required facet and query type.

2. The neutral bundle

Second, I adjusted the neutral bundle used for query generation. In the last round I passed the title into the query generator — and if the title also gets used in scoring on the retrieval side (that is, if the title sits in the dataset metadata), you get the echo problem. The LLM generating a query is quite likely to adopt the title outright or rewrite it only weakly, which then lands precisely on the title in the metadata and makes retrieval performance look extremely good.

Auctus’ default production setup, however, actually runs hybrid retrieval — lexical BM25 plus a dense vector k-NN score — and the lexical half uses OpenSearch’s best_fields, which combines the per-field matches by taking the strongest one rather than adding them together. With the title weight set to 2, the scoring formula is:

score = max(2 × title_BM25, arm_BM25) + knn_score

The first round’s approach sidestepped the problem by turning the title off and scoring on the description field alone:

score = arm_BM25

That’s clean, certainly, but it has no reference value. So why do I want to use Auctus’ default hybrid retrieval this round? Because in the real world, using the title in retrieval — including giving the title a high weight — is the more reasonable setup. Imagine you know a dataset’s exact title: then of course you ought to be able to search that dataset up directly. A dataset title can be understood as a human-readable version of a unique identifier; if you could search the dataset ID directly, that’s an even more certain hit. If a system can’t manage that, it’s fairer to call it a problem with the retrieval system. A user who already knows the exact title has no need of a better description, because they can find the dataset through the title directly. Most real users are the ones who know what they need but not what it’s called. Having made that argument: the query-generation side and the retrieval side can’t both use the title, and taking the title out of query generation both fixes the echo problem and lands closer to that more realistic scenario.

And it’s right here that the second problem shows up. As a ranking rule, best_fields is a reasonable default. As an evaluation rule, it’s a disaster. Whenever 2 × title_BM25 > arm_BM25, that max throws away the description’s contribution entirely — which is to say, every description strategy under comparison receives exactly the same score on that candidate. The differences between data representations that the benchmark is supposed to detect get wiped out. So for this round I designed an additive variant, summing the two lexical contributions instead of taking the larger:

score = 2 × title_BM25 + arm_BM25 + knn_score

The title keeps its real weight and its real influence on the ranking, but no matter how strongly the title matches, each strategy’s own score always counts toward the total.

3. Validating the removal of the title

A natural concern: given that the title is such important topical information, can I still generate queries that fit a dataset’s actual situation once I take it out of query generation? To begin with, the bundle I generate queries from is certainly not just the title — I won’t disclose the specific design. My principle has always been that intuition guides my design, but I can’t believe intuition blindly; if something can be validated, validate it.

I selected some datasets with the shortest description lengths from the new sample, and from among those picked out the seven with the fewest effective characters as hard samples, then built bundles for them with the new query-generation pipeline. I then had a more advanced flagship model (my query generator and judges are all the cheapest models) read them blind, guess the subject from these neutral bundles, and compare it against whether the real title’s subject matched. Six matched completely and one was uncertain. After my own manual review, I judged all six as passing, and counted the uncertain one as passing too: the dataset’s subject type was right, but the source agency was wrong — and even the guessed agency type was quite similar — plus that dataset has only two records in total, so there’s very little useful information in it. All told, the new title-free query generation pipeline is entirely reasonable and safe.

4. Adjusting the judges

Finally, I made adjustments to the judges. First, I moved to graded qrels rather than the last round’s binary, which fits the new judging logic: subject wrong (0), subject right but the facet’s constraint wrong (1), both subject and constraint right (2). Second, the prompt adopts the framework from the Noy paper (https://arxiv.org/pdf/2605.28787). Third, I selected the judge models carefully.

The first two are adjustments to the prompt: I adopted a successful paper’s framework and added few-shot prompting. For selecting the judge models, I first tested mechanical feasibility — the temperature=0 setting, the prefix-caching mechanism, how self-consistent a model is, and how fast it runs — which filtered out a batch of models. In the second round I had the candidate models judge a portion of the samples, then used a more advanced model (again, the models I chose are all the cheapest, fastest ones) plus manual review to compare how consistent the results were, and settled on the judge models from there.

query ─→ retrieval score ─→ ranked list ┐
                                        ├─→ NDCG@k
judge ─→ qrels (merged judges) ─────────┘

5. Did the max rule collapse the comparison?

One thing I was interested in is the worry raised earlier: does the max_of_fields combining rule (max(w×title, arm) + knn), with the title weight set high, actually degenerate into “look only at the title match plus some dispensable decimal tail,” and thereby distort the discrimination between the six arms?

There’s a mathematical relationship here that can be proven. additive and max_of_fields are not two independent quantities — they differ by exactly one quantity you can write down:

additive        = w×title + arm + knn
max_of_fields   = max(w×title, arm) + knn
─────────────────────────────────────────
additive − max_of_fields = min(w×title, arm)

Because the title, arm, and knn scores are all non-negative, what max_of_fields discards is precisely the smaller of title and arm. Measuring how much gets discarded with a discard ratio, discard / additive, gives a hard upper bound:

discard / additive ≤ (w×title + arm) / 2 / (w×title + arm + knn) ≤ 0.5

Equality requires knn=0 and w×title = arm exactly. Which is to say: no matter how strongly the title matches, max_of_fields discards at most half the total score relative to additive, and cannot discard more. In the actual measurements, every arm’s maximum discard ratio bore this boundary out — not one of them broke through it, and all of them landed right up against it. And visualizing the shape of the discard-ratio distribution, it’s bimodal, with the two peaks near 0 and near the upper bound and nothing in between, consistent with the bound derived above.

So on the whole, I can say this degeneration did not happen: mathematically it’s ruled out. It does, however, systematically favor candidates whose title match is stronger, which is why the additive variant is worth keeping. And given that I don’t pass the title into the query-generation side, any match against the title is purely the model’s rewrite happening to hit it. Compared to the outright title leakage in Keywords are not always the key, this actually simulates a real user’s search more closely — after all, users may well search using the dataset title’s original words.
