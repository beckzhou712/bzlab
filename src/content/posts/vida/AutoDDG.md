AutoDDG (Automated Dataset Description Generation) is a framework that automatically generates natural-language descriptions for tabular data. It summarizes a dataset's metadata through a data-driven method and enriches the semantic information with a large language model, producing descriptions that are readable, comprehensive, and accurate. It is developed, maintained, and open-sourced by the VIDA Center team ([GitHub](https://github.com/VIDA-NYU/AutoDDG)), and published at SIGMOD 2026 (Proceedings of the ACM on Management of Data, PACMMOD) ([arXiv](https://arxiv.org/abs/2502.01050)).

## What problem does AutoDDG solve?

![Fig. 1 from the paper: three dataset descriptions from NYC Open Data alongside a description generated by AutoDDG and one generated by an LLM from a data sample.](../../attachments/Screenshot%202026-08-13%20at%2016.32.45.png)

First, the original descriptions on public data portals are too brief, inconsistent with the dataset's actual content, or missing outright. Descriptions like these offer users limited insight. A rich description helps a user judge earlier whether a dataset is useful, without having to take further steps such as downloading or exploring it.

Second, the dataset search systems these portals support follow the web search paradigm: keyword queries over metadata such as the dataset's name, description, and size. Metadata quality is therefore critical — metadata should convey the dataset's content effectively, both to fit what users are searching for and to keep retrieval accurate. If a dataset's description drifts from its actual content, a dataset retrieved on the strength of that description may satisfy the query semantically while failing to meet the user's need for the actual data. Google Dataset Search, for instance, excludes datasets lacking descriptions from its index outright.

## Applying LLMs to description generation: pros and cons

**Pros:**

- An LLM's ability to produce fluent, readable text, together with its broad world knowledge, lets it generate coherent descriptions rich in inferred semantics and contextual information.

**Cons:**

- A mismatch in data form. LLMs are meant to process and generate text, whereas datasets are tabular. This mismatch raises the question of how best to represent a table inside a prompt.
- Context window limits. The context window means a large dataset cannot be fed to the LLM in full, and relying on sampling alone yields descriptions that are incomplete and misleading about the dataset as a whole.
- Hallucination is hard to eliminate.

## The AutoDDG architecture

![Fig. 2 from the paper: the AutoDDG pipeline, with a content profiler and an LLM-powered semantic profiler feeding a description generation engine that emits user-focused and search-focused descriptions.](../../attachments/Screenshot%202026-08-13%20at%2017.01.16.png)

AutoDDG uses a two-stage architecture.

The first stage is **Context Preparation**, which profiles the dataset in two complementary ways. The outputs of the two profilers are combined into the dataset context used for the description generation that follows.

- **Content profiling** captures the dataset's statistical properties algorithmically. This step anchors the LLM's description in the dataset's actual content, avoiding the uncontrolled hallucination that comes of having the LLM handle raw data directly. The paper uses the Datamart Profiler.

  ![Fig. 3 from the paper: an example content summary listing row and column counts, and per-column data types, coverage, and unique value counts.](../../attachments/Screenshot%202026-08-13%20at%2021.17.20.png)

- **Semantic profiling** uses an LLM to supply contextual information not stated explicitly in the data — the dataset's topic, say, or the kinds of analysis it supports — improving discoverability through keywords and topical clues. For each column in the dataset it generates a prompt containing the column name, sample values, and data type. The LLM returns a JSON classification of the column against predefined semantic categories. The structured output is then serialized into descriptive sentences, and the summaries for all columns are concatenated to form the semantic profiler module's final output.

  ![Fig. 4 from the paper: the SemanticProfiler algorithm, with two examples of semantic information derived from a Year column and a Liabilities column.](../../attachments/Screenshot%202026-08-13%20at%2021.33.08.png)

The second stage is **Description Generation**, where an LLM-based engine uses the summaries from Context Preparation to generate descriptions. AutoDDG supports two kinds: User-Focused Descriptions (UFD) and Search-Focused Descriptions (SFD).

- **UFD** is aimed at users and concerned with readability: informative, clear, and more concise than an SFD.
- **SFD** is aimed at search, meant to make a dataset more discoverable in a search system; it merges an overview of the dataset with an expansion of topic-related terms. Suppose a user wants to publish a dataset about "climate data" containing detailed measurements for various regions. The system identifies "climate data" as the topic and enriches the description by adding climate-related keywords such as "temperature trends," "precipitation levels," "regional climate analysis," and "weather patterns." Folding in topic-related terminology this way raises the probability that users searching for climate-related datasets will find this one.

Descriptions produced by AutoDDG can be indexed by standard search engines such as Elasticsearch and OpenSearch, and can also be used to create embeddings — improving discoverability without major changes to existing infrastructure.

### BTW — how a description supports dataset retrieval

**Indexing by a standard search engine (lexical retrieval).** A standard search engine typically processes all descriptions into an inverted index, finding the descriptions that contain the query's terms. When a user searches for _taxi_, the engine can identify which datasets have _taxi_ in their description. Beyond whether a term appears, the engine also records term frequency, term positions, and similar information — it knows not only whether a description contains _taxi_ but how many times it occurs and where. The engine then combines these signals (via BM25, for example) into a relevance score and returns results ranked by that score.

**Embedding.** Here the entire description is turned into a high-dimensional vector by an embedding model, and the user's search input goes through the same model to become a query vector. Results are then returned ranked by a similarity measure such as cosine similarity, computed between the query vector and each dataset description vector.

Search engines built on an inverted index generally use lexical retrieval, whose strength is exact matching on query terms — an advantage when you need to retrieve a specific term or keyword precisely. Embedding-based retrieval, by contrast, draws on the semantic relationships the model learned during training, placing expressions that are semantically close but lexically different nearer to each other in vector space, which gives it better semantic matching.

### AutoDDG's advantages

AutoDDG requires no training and generalizes across domains. The descriptions it generates are accurate, readable, and highly effective for retrieval. The paper proposes a comprehensive evaluation method for the quality of generated descriptions, covering these dimensions:

- how much dataset retrieval improves when the automatically generated descriptions are used;
- the similarity between the generated descriptions and existing ones, where they exist, to assess AutoDDG's ability to produce descriptions close to human-written ones;
- intrinsic text-quality metrics, using an LLM as judge and validated by human experts, to assess linguistic dimensions such as readability and conciseness;
- the cost and scalability of the approach.

## Evaluation

### Three evaluation strategies

- **Dataset retrieval evaluation** assesses the effect of descriptions on search effectiveness.
- **Reference-based evaluation** compares automatically generated descriptions against existing ones.
- **Reference-free evaluation** uses an LLM to assess descriptions without reference text.

#### Dataset Retrieval Evaluation

To measure retrieval performance, the paper adopts the Normalized Discounted Cumulative Gain (NDCG@k) metric. NDCG@k measures ranking effectiveness by comparing the ideal ordering of relevant items against the system's actual top-k ordering up to position k. It accounts for both a dataset's relevance and its rank, assigning a higher score the earlier a dataset appears.

#### Reference-Based Evaluation

For datasets that already have an original description, the generated description can be compared against it. The following metrics give a structured, quantitative assessment of how well the generated description matches the reference in wording, content, and meaning:

- **METEOR:** combines precision, recall, a synonym dictionary, and stemming to allow a more flexible comparison between the generated and reference descriptions.
- **ROUGE:** recall-oriented, evaluating by measuring the overlap in n-grams, longest common subsequence, and skip-bigrams between the generated and reference text.
- **BERTScore:** uses a pretrained language model such as BERT to measure embedding similarity between the generated and reference text. The paper uses the F1 variant of BERTScore.

#### Reference-Free Evaluation

This assesses the quality of the generated descriptions, and divides into LLM-as-judge and expert evaluation.

LLM-based evaluation divides further into two methods:

- **Pointwise evaluation.** Adopts G-Eval's prompt design and example evaluations, scoring each description individually against these criteria: completeness, conciseness, and readability.
- **Pairwise evaluation.** Two candidate descriptions are presented to the LLM, which is asked to choose the better one. For each dataset, ten unordered pairs are sampled uniformly at random from the descriptions generated by the different methods. Each pair is judged twice — once in each presentation order — to mitigate positional bias. Again, the LLM assesses the candidates on completeness, conciseness, and readability. The reported figure is the win rate: the number of wins divided by the total number of pairwise comparisons the method took part in.

It has to be acknowledged that LLM-based evaluation can introduce biases inherent in the model's training data. To mitigate this, the paper uses cross-evaluation — Llama evaluates the descriptions generated by GPT, and vice versa.

**Expert evaluation.** Three annotators evaluated 48 stratified-sampled datasets across four description types: the AutoDDG variants (SFD-GPT and UFD-GPT), the original descriptions, and LLM-GPT. The annotators rated four dimensions on a 1–10 scale: completeness, conciseness, and readability (matching the automated metrics), plus faithfulness — the degree to which a description accurately conveys the actual dataset content, including the dataset's variables, structure, and statistics, without hallucination or factual error. Inter-annotator agreement (IAA), and the agreement between the LLM judges and the humans, were assessed using Pearson's r over z-score-normalized ratings, comparing GPT's and Llama's evaluations against the normalized human consensus.

### Benchmarks

The paper adapts ECIR and NTCIR into ECIR-DDG and NTCIR-DDG as benchmarks. Each benchmark contains:

- queries
- datasets collected from open data portals
- relevance triples — qrels of the form (dataset, query, relevance)

### Retrieval Performance Metrics

BM25 and SPLADE are used as the metrics.

BM25 is a criterion that handles scoring and ranking once term matches have already been found; it belongs to the lexical matching covered in the aside above. When a user searches for _NYC taxi fare_ and several dataset descriptions contain _taxi_, BM25 scores and ranks them by weighing additional factors. Specifically, BM25 considers three factors:

- **Containment.** A description covering more of the query terms has the advantage. One containing NYC, taxi, and fare together scores higher than one containing only NYC.
- **Frequency of occurrence.** A description where the query term occurs more often has the advantage. A description with two occurrences of NYC scores higher than one with a single occurrence — though under BM25 the gain from additional occurrences diminishes.
- **Rarity of the query term.** If NYC appears 1,000 times across the whole data portal while taxi appears only 100, BM25 gives taxi a higher weight through IDF (inverse document frequency).

The BM25 formula:

```text
                    f(t,D) · (k₁ + 1)
score(D,Q) =  Σ    ─────────────────────────────────────  · IDF(t)
             t∈Q    f(t,D) + k₁ · (1 − b + b · |D|/avgdl)
```

SPLADE stands for Sparse Lexical and Expansion model. SPLADE retrieves documents using vector search over sparse text representations, which are derived by expanding query terms with semantically related words using a neural network (like BERT). For example, it may expand 'lunar' to include 'moon', thereby capturing broader context.

### Results

#### Retrieval Performance

In the BM25 results, AutoDDG-SFD outperformed UFD on both ECIR-DDG and NTCIR-DDG, confirming SFD's effectiveness for retrieval. In the SPLADE results, SPLADE's semantic term expansion in vector space achieved substantial gains over BM25 on the original descriptions. This is what one would expect, since AutoDDG and SPLADE take different approaches to expanding the information contained in the original description. **Combining SPLADE with AutoDDG descriptions, however, worked best of all.** See the paper for the full results.

#### Evaluation of Dataset Description Quality

**Reference-based evaluation.** AutoDDG-UFD performed exceptionally well on METEOR, indicating improved semantic consistency with the reference descriptions. AutoDDG-SFD scored higher on ROUGE, marking greater overlap with the exact terms and phrases of the reference text. This fits the typical goal of a search-focused description: ensuring high-precision matching on key data points. The AutoDDG methods scored slightly below the LLM-only baseline on BERTScore, likely because BERTScore favors embedding similarity to text phrased like the reference. AutoDDG, by contrast, prioritizes factual grounding, generating descriptions that are semantically accurate but linguistically varied — as its competitive METEOR and ROUGE scores confirm. See the paper for the full results.

**Reference-free evaluation.**

- **AutoDDG-UFD-GPT** stood out on **conciseness** and **readability**, confirming the expectation that user-focused descriptions prioritize clarity and readability. This reinforces the design decision to create user-centered descriptions.
- **AutoDDG-SFD-GPT**, conversely, ranked highest on **completeness**, matching the expectation that search-focused descriptions prioritize comprehensive data coverage — even at the cost of readability or conciseness.

The LLM-only methods achieved competitive conciseness scores because they generated shorter descriptions without profiling the data, but their markedly lower completeness scores highlight how incomplete their grasp of the data is.

Note the differences between model arms. The GPT arm performed better than the Llama arm, but the gap between the two is far less pronounced than the gap between SFD and UFD. This says that AutoDDG performs better with a better model, but that a weaker model comes very close to the stronger one — good news for cost control.

In the human evaluation, three users assessed **faithfulness** by comparing the generated descriptions against the original datasets. AutoDDG's descriptions were significantly more faithful than those derived from LLM-GPT. This suggests that combining data profilers with a topic generator effectively reduces hallucination and factual error — a key advantage over pure LLM generation. LLM-only descriptions frequently contained factual errors, including wrong time ranges, inaccurate statistics, and unfounded inferences; the AutoDDG methods largely eliminated these. Users did occasionally see errors in AutoDDG descriptions, which were traced back to bugs in the algorithmic profiler — misjudging temporal coverage or units of measurement, for instance. Even so, the generated descriptions remained consistent with the information the profiler reported. Human annotators' scores also correlated strongly with the LLM-derived ones (r = 0.72).

#### Ablation Study

The paper runs an ablation study comparing the variants below, and finds that the complete AutoDDG — with all components included — achieves the best performance, further confirming its role in improving search relevance. SP stands for Semantic Profiler.

- **AutoDDG-noSP-noSFD:** generates descriptions without SP or SFD, relying only on basic dataset sampling and statistics.
- **AutoDDG-noSFD:** includes SP but omits SFD, using semantic insight to enrich the description without optimizing specifically for search retrieval.
- **AutoDDG-noSP:** includes SFD but omits SP, testing a configuration optimized specifically for search retrieval without SP.
- **AutoDDG:** includes both SP and SFD, drawing on semantic insight while also optimizing descriptions for search retrieval.

## Future directions

- Multimodal approaches that incorporate other data modalities.
- Improving the profiler.
- Strategies for detecting and controlling LLM hallucination, so that descriptions remain strictly faithful to the dataset's content and context, are an important research direction.
- Human-in-the-loop techniques, which offer an opening to further improve accuracy, completeness, and trustworthiness, particularly in high-stakes domains.
